# Internationalization and localization standard

This is the normative standard for future multilingual zMovie UI, API
messages, CLI presentation, and documentation examples. The current static UI
is English-only and does not yet implement runtime locale catalogs. Following
this guide does not change that status.

## Locale identifiers

- Use valid BCP 47 language tags with canonical casing, such as `en-US` and
  `th-TH`.
- `en-US` is the source and default locale. `th-TH` is the first additional
  locale; every later locale must be explicitly registered and tested.
- Use the same locale contract in browser state, API negotiation, generated
  metadata, tests, and documentation.
- Set the HTML `lang` attribute and effective text direction from the active
  locale. Do not infer direction from user-entered text.

## Message catalogs

- Keep user-facing strings in locale catalogs with stable, namespaced keys,
  for example `studio.project.create`.
- Keep labels, help, errors, validation, accessibility names, loading states,
  empty states, and notifications in the same translation contract.
- Never use translated text as a key, use sentence fragments as keys, or
  concatenate fragments to form a sentence.
- Use ICU-style interpolation, plural, and select messages when supported by
  the chosen runtime. Preserve variable names, types, and required placeholders
  across all catalogs.
- Keep developer logs, API field names, environment variables, CLI flags, and
  persisted identifiers as stable English technical contracts unless the API
  defines a separate localized presentation field.

## Formatting and accessibility

Use locale-aware platform formatting APIs for all presentation values:

- `Intl.DateTimeFormat` for dates and times;
- `Intl.NumberFormat` for numbers, percentages, and currencies;
- `Intl.ListFormat` for lists; and
- the platform relative-time formatter for relative dates.

Stored numeric values and currency amounts must not change when a display
locale changes. Every timestamp needs an explicit timezone policy. Allow for
text expansion, long translated labels, screen-reader names, keyboard use,
and right-to-left layout without clipping or reordering meaningful controls.

## Fallback and API behavior

Resolve a requested locale in this order:

1. exact registered locale;
2. registered language-only locale; and
3. `en-US`.

Missing keys must be visible to developers and CI and must fall back safely in
production without exposing raw key names to users. API clients may send
`Accept-Language`; the service must validate the tag, document the selected
fallback, and keep machine-readable error codes stable while human-readable
messages may be localized.

## Translation workflow

When a source message changes:

1. update every catalog or record an explicit fallback decision;
2. preserve placeholders, plural/select branches, markup boundaries, and
   accessibility semantics;
3. review Thai and every other translation for meaning, tone, safety, length,
   and platform limits; and
4. run catalog syntax, key-parity, duplicate-key, placeholder-parity, and
   plural/select-structure checks.

Machine translation may assist drafting but is not final review. Do not place
credentials, private paths, personal data, or provider-specific secrets in a
translation value.

## Documentation and rollout

Technical documentation remains English unless a translated guide is explicitly
maintained. Localized examples must label the locale and keep technical names
unchanged. A future runtime implementation must add catalogs, locale
negotiation, fallback telemetry, accessibility tests, and browser/API tests
before claiming localized UI support.
